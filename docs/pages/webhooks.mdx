# Webhooks

VerifyAfrica can POST verification events to your server so you do not need to poll for results.

Webhooks fire for verifications created from the **dashboard**, **public API**, **bulk uploads**, and other internal flows — as long as your tenant webhook is configured and active.

## Setup

Configure webhooks in the VerifyAfrica dashboard under **API Keys**:

1. Add your HTTPS endpoint URL (for example `https://your-app.com/webhooks/verify-africa`)
2. Optionally enable authentication and copy the webhook token
3. Keep the webhook **Active**

There is no public API endpoint to create or update webhooks — configuration is dashboard-only.

## Event

| Field | Value |
| --- | --- |
| Event name | `verification.completed` |
| HTTP method | `POST` |
| Content-Type | `application/json` |
| Timeout | 30 seconds |

Delivery happens after VerifyAfrica finishes initiating the verification with the provider. Check `data.status` for the current result (`pending`, `success`, `failed`, and other statuses). For some hosted flows the first delivery may arrive while the check is still `pending` — use `GET /api/v2/public/verifications/requests/?verification_id={id}` if you need a later refresh.

## Headers

| Header | Description |
| --- | --- |
| `Content-Type` | Always `application/json` |
| `Authorization` | Present when webhook auth is enabled: `Bearer <webhook_token>` |

Verify the `Authorization` header against the token shown in the dashboard before trusting the payload.

## Payload

```json
{
  "status": "success",
  "event": "verification.completed",
  "data": {
    "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "verification_type": "aml_screening",
    "status": "success",
    "input_data": {},
    "response_data": {},
    "cost_charged": "1.00",
    "currency": "USD",
    "created_at": "2026-07-16T14:30:00.000Z",
    "batch_id": null,
    "reference": "VER-019abc...",
    "link": null,
    "email_sent_at": null,
    "by_api": true,
    "api_key_id": "..."
  }
}
```

### Top-level fields

| Field | Type | Description |
| --- | --- | --- |
| `status` | string | Delivery envelope status. Always `"success"` when the event is sent. |
| `event` | string | Always `"verification.completed"`. |
| `data` | object | Verification request details (same shape as create/retrieve responses). |

### `data` fields

| Field | Type | Description |
| --- | --- | --- |
| `id` | string (UUID) | Verification request ID. |
| `verification_type` | string | Product type (e.g. `aml_screening`, `ng_bvn_verification`). |
| `status` | string | Verification status (`pending`, `success`, `failed`, …). |
| `input_data` | object | Input submitted for the check. |
| `response_data` | object | Provider response payload when available. |
| `cost_charged` | string | Amount charged for the request. |
| `currency` | string | Charge currency (e.g. `USD`). |
| `created_at` | string | ISO 8601 timestamp. |
| `batch_id` | string \| null | Present when the request was part of a bulk batch. |
| `reference` | string | Internal verification reference. |
| `link` | object \| null | Hosted-link details when applicable. |
| `by_api` | boolean | `true` when created via the public API. |
| `api_key_id` | string \| null | API key used for public API creates. |

## Responding

Your endpoint must return **HTTP 200** for the delivery to be considered successful.

Any other status code (or a network/timeout failure) is treated as a failed delivery.

## Retries

Failed deliveries are retried automatically via Celery:

| Setting | Value |
| --- | --- |
| Max retries | 3 |
| Delay between attempts | 30 seconds |
| Success condition | HTTP `200` from your endpoint |

After all retries are exhausted, VerifyAfrica stops attempting that delivery. You can still fetch the verification with the public retrieve endpoint.

## Example handler

```javascript
import express from "express";

const app = express();
app.use(express.json());

const WEBHOOK_TOKEN = process.env.VERIFY_AFRICA_WEBHOOK_TOKEN;

app.post("/webhooks/verify-africa", (req, res) => {
  const auth = req.header("authorization") || "";
  if (WEBHOOK_TOKEN && auth !== `Bearer ${WEBHOOK_TOKEN}`) {
    return res.status(401).json({ error: "Unauthorized" });
  }

  const { event, data } = req.body;

  if (event === "verification.completed") {
    // Handle the verification result
    console.log(data.id, data.verification_type, data.status);
  }

  // Must return 200
  return res.status(200).json({ received: true });
});
```

## Best practices

- Use HTTPS endpoints only
- Validate the `Authorization` bearer token when auth is enabled
- Return `200` quickly; process heavy work asynchronously in your system
- Treat `data.status` as the source of truth for the verification outcome
- Idempotently handle retries using `data.id` (the same verification may be delivered more than once)
