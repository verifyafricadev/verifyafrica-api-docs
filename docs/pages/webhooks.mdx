# Webhooks

VerifyAfrica can POST verification events to your server so you do not need to hold open HTTP connections or poll for results.

Webhooks fire for verifications created from the **dashboard**, **public API**, **bulk uploads**, and other internal flows — as long as your tenant webhook is configured and active.

:::tip Source of truth
Event names, `verification_type` values, statuses, and the full payload shape are defined in the OpenAPI schemas:

- [Webhook events & payload](/api/webhooks) — `verification.completed` and `verification.failed`
- Schemas: `WebhookEvent`, `PublicVerificationType`, `VerificationStatus`, `WebhookPayload`

Prefer those schemas over copying examples from this page.
:::

## Public API + webhooks

Public create endpoints return **immediately** with `status: PENDING`.

- **Link mode** (document / facial / address with `mode: "link"`) — customer still needs to open `data.link.url`. Terminal webhook fires after they finish capture and processing completes.
- **Direct mode** (proof URLs, or any other product) — provider work starts in the background. Terminal webhook fires when verification completes.

Recommended flow:

1. `POST` a product create endpoint (include `mode` for document / facial / address)
2. Store the returned `data.id` (and `data.link.url` when using link mode)
3. Wait for `verification.completed` or `verification.failed` on your webhook URL
4. Optionally poll `GET /api/v2/public/verifications/requests/?verification_id={id}` if needed

## Setup

Configure webhooks in the VerifyAfrica dashboard under **API Keys**:

1. Add your HTTPS endpoint URL (for example `https://your-app.com/webhooks/verify-africa`)
2. Optionally enable authentication and copy the webhook token
3. Keep the webhook **Active**

There is no public API endpoint to create or update webhooks — configuration is dashboard-only.

## Events & types

Each OpenAPI schema maps to a specific key in the webhook JSON body:

| Schema | Payload key | What it defines |
| --- | --- | --- |
| `WebhookPayload` | *(root body)* | Full JSON object POSTed to your endpoint |
| `WebhookEvent` | `event` | `verification.completed`, `verification.failed` |
| — | `status` | Envelope status: `success` or `failure` (aligned with `event`) |
| `VerificationRequestData` | `data` | Verification object nested under the root payload |
| `PublicVerificationType` | `data.verification_type` | Every public-API product type value |
| `VerificationStatus` | `data.status` | Lifecycle statuses (`PENDING`, `SUCCESS`, `FAILED`, `ERROR`, …) |
| `TerminalVerificationStatus` | `data.status` (subset) | Statuses that trigger a terminal webhook (`SUCCESS`, `FAILED`, `ERROR`) |

| Event (`event`) | When | Envelope `status` | Typical `data.status` |
| --- | --- | --- | --- |
| `verification.completed` | Verification finished successfully | `success` | `SUCCESS` |
| `verification.failed` | Verification did not succeed | `failure` | `FAILED` or `ERROR` |

No webhook is sent while the verification is still `PENDING`.

## Payload shape

Webhook `data` uses the same public shape as GET detail responses. It is **provider-agnostic**:

- No internal provider names
- No provider-hosted proof URLs, access tokens, or verification links
- `input_data` is the resolved request (mode, capture flags, collect for documents, nested document/face/address). Proof HTTPS URLs you submitted are kept; provider-hosted assets are not.
- For link-mode identity products, `link.url` is the customer capture URL
- For direct mode, `proofs` / `input_data.*.proof` echo the HTTPS URLs you submitted
- `response_data` contains the verification result with upstream artifacts stripped

## Delivery details

| Field | Value |
| --- | --- |
| HTTP method | `POST` |
| Content-Type | `application/json` |
| Timeout | 30 seconds |
| Auth header | `Authorization: Bearer <webhook_token>` when auth is enabled |

## Responding

Your endpoint must return **HTTP 200**. Any other status (or network/timeout failure) is retried up to **3** times with a **30s** delay.

## Example handler

```javascript
import express from "express";

const app = express();
app.use(express.json());

const WEBHOOK_TOKEN = process.env.VERIFY_AFRICA_WEBHOOK_TOKEN;

app.post("/webhooks/verify-africa", (req, res) => {
  const auth = req.header("authorization") || "";
  if (WEBHOOK_TOKEN && auth !== `Bearer ${WEBHOOK_TOKEN}`) {
    return res.status(401).json({ error: "Unauthorized" });
  }

  const { event, data } = req.body;

  // event values: see schema WebhookEvent
  if (event === "verification.completed") {
    console.log("passed", data.id, data.verification_type, data.status);
  } else if (event === "verification.failed") {
    console.log("failed", data.id, data.verification_type, data.status);
  }

  return res.status(200).json({ received: true });
});
```

## Best practices

- Use HTTPS endpoints only
- Validate the bearer token when auth is enabled
- Return `200` quickly; process heavy work asynchronously
- Switch on both `event` and `data.verification_type` using the OpenAPI enums
- Idempotently handle retries with `data.id`
